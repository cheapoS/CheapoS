# Taking over a stalled task

Unattended work keeps its normal guardrails. When an authorized task pauses or
fails, type a direction in its chat and choose **Take over & continue**. That
single action enables human-directed development for this task and continues
from its saved files. It does not require a separate settings visit. A routine
question from an agent still uses the ordinary reply flow.

During takeover, cumulative token, turn, working-time and automatic recovery
attempt caps no longer stop the work. Repeated reads receive feedback without
removing inspection tools. Verification commands within the task copy are
permitted by the takeover action; captured branch checks are reauthorized.
Usage, costs, failed attempts, earlier instructions and review evidence remain
recorded. Explicitly setting bounded work limits can restore work caps.

Send another direction while work is active to interrupt the old response and
continue on the same runtime. A stale response cannot apply its queued edits
after the correction is accepted. An active response body can be cancelled;
a provider still establishing its connection may take until the existing
connection timeout to return. Stop remains available.

Recovery controls also offer an eligible worker replacement and, for a branch
run, revision of the current unfinished item's instructions. These changes are
explicitly approved and tied to the current task revision. Committed items,
accepted criteria and required checks retain their evidence and authority.

Development mode can also be selected for new tasks in execution settings.
Changing that default does not silently change existing tasks.

## What completion still means

Takeover removes workflow retry and work-budget obstacles. It does not make an
unavailable provider available, invent tool capabilities, approve spending on
new paid routes, mark failed checks as passed, or merge unfinished work. Existing
spending policy, task-copy boundaries, command validation and independent review
still apply. Actual environment or authorization failures are shown with a
specific continuation explanation, alongside the saved direction.

## Verification of this change

A disposable real HTTP/engine fixture was deliberately stalled by repeated
inspection. A single takeover request then edited the saved fixture, ran its
three verification assertions (0.11 seconds), and reached reviewer approval.
All seven scripted requests remained accounted for (140 synthetic tokens);
no external model calls were made. A second deterministic case verifies that a
live correction rejects an old response's proposed write and continues on the
same runtime with cumulative usage intact.

The new operator engine cases take about 1.3 seconds together; the smallest live
redirect case measured 0.415 seconds. Twelve pure branch controls cases measured
0.066 seconds, and five development-policy cases approximately 0.002 seconds.
These use small fixtures, not a new multi-item workflow suite. Existing scoped
permission and transport checks are reused.

Synthetic browser interaction covered the recovery controls. The browser
blocked the separate real-backend fixture with ERR_BLOCKED_BY_CLIENT, so that
combined browser flow was not verified; its backend continuation was verified
through the local HTTP API instead. The personal application was not restarted.

## Continuing after repeated inspection

Compacted context now retains the latest operator direction, bounded prior worker
statements (explicitly unverified), completed-item summaries and recent check
receipts. Its next-step guidance distinguishes missing verification from a passed
check for the same patch and workspace generation. Check input identities and
accepted command coverage still require validation by the normal checkpoint path.
Development recovery keeps inspection tools available and follows the repository's
scoped-testing policy. Existing accepted full-suite requirements are not silently
removed; they must be explicitly addressed as plan requirements.

Deterministic coverage exercises repeated compaction of a stalled fixture and
stale patch/generation rejection. This verifies the supplied context, not a claim
that a particular live model will always follow it. No live run was resumed.
