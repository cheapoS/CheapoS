# CheapOS check-in — September 13, 2026

**Status:** planning reference, not a record of newly implemented features. Code baseline: `e5bddde`.

CheapOS has a working agent loop. The next milestone is making that loop feel dependable and easy to direct: open a project, explain the job, watch CheapOS work, then approve a finished result.

**My recommendation: prioritize fewer unnecessary interruptions, clear navigation, and reliable completion before adding more models or optimization layers.** Free tokens are useful, but an agent that burns an evening and requires twenty interventions is still expensive in human time.

Our product boundary still makes sense:

> CheapOS decides why and when to spend intelligence. OmniRoute decides where to get it.

CheapOS should own the conversation, task state, tools, verification, permissions, and final decision. OmniRoute should own provider connections, credentials, quotas, and provider routing. Keep direct local inference available so the gateway remains optional.

## 1. What we have accomplished

| Area | Present today | What remains unproven or incomplete |
| --- | --- | --- |
| Local product | Python/Git application with a browser UI, no CheapOS account or hosted project requirement | Packaged desktop distribution and effortless first-run setup |
| Project conversation | Open a repository, ask questions, request edits, steer a running task, continue after review and commit | Clear task names, manageable sidebar history, consistently obvious next actions |
| Agent orchestration | Local delegation, all-local, all-remote, and manual worker/reviewer choices | Reliable selection for a range of real tasks, not just a successful tool probe |
| Visible work | Worker, checks, and reviewer grouped inside CheapOS replies; expandable live details and thinking; Pause beside the composer | A calmer default view and clearer explanations of automatic recovery |
| Repository tools | File listing/search/reading, edits, compact line editing, tracked file versions, public text URL reading | Better project orientation, dependency setup, and larger-project navigation |
| Verification and review | Real test execution, streaming output, separate reviewer, revision loop, reuse of matching passing checks | Better test selection, predictable runtimes, fewer repeated approvals |
| Delivery | One human approval applies the reviewed patch and commits locally; request changes or decline remain available | More understandable Git status and recovery across concurrent chats |
| Recovery | Saved task copies, pause/resume, bounded free-model handoffs, cooldowns, malformed-output recovery, same-chat conflict reconciliation | Less manual babysitting and stronger long-run success evidence |
| Closing the loop | Successful commit prompts the operator for the next task | Better task naming and history as one conversation grows |

There is a documented **30.73-second live delegation → edit → verification → different-model approval** result in [the delegation experiment](docs/experiments/2026-09-13-delegation.md). That demonstrates the mechanism on a tiny fixture. It does not establish overnight reliability, broader code quality, or measured savings versus another agent. Its $0.00 accounting used configured prices, not a provider billing receipt.

The latest completed development checks were **299 Python tests in 295.917 seconds**, **60 JavaScript tests passing**, and browser checks of Pause, draft preservation, tab switching, and a narrow viewport. The Python duration is from the preceding implementation run on this machine, not a cross-machine benchmark.

## 2. What the product should feel like

The operator should interact with one assistant:

> **CheapOS:** I’ll add the CSV converter and check its edge cases.  
> Working on the converter · Details  
> Running the selected tests · Details  
> Getting a second opinion · Details  
> Ready: 2 files changed. Checks passed. Review approved.  
> **Approve & commit** · **Request changes** · **Decline**

After approval:

> **CheapOS:** Committed the CSV converter. What would you like to work on next?

Keep named models, elapsed time, real output, failures, and evidence available in Details. Activity becomes the deeper history rather than a second competing conversation. Never fabricate activity to look busy; show waiting, cooldown, or the current command honestly.

### Task title and sidebar

Replace the main `CheapOS / Chat` breadcrumb with the **task title**. Show the project as a smaller secondary label or folder button. Keep the CheapOS identity in the app branding and assistant messages. Avoid repeating the title in two stacked header rows.

Current titles are the first 90 characters of the initial prompt. That creates entries such as “hi” and truncated requirement paragraphs. Derive a useful title from the first substantive request, allow manual rename, and never overwrite a user-edited title. Simple naming should not require another model request.

Add a visible overflow menu to each chat with **Rename, Pin, Archive, and Delete**. Add collapsed project groups, full-history access, and clear running/needs-attention/completed states. The current renderer shows only the first twelve tasks per project; the rest should have a discoverable “Show more,” not disappear from the normal navigation.

Deletion needs understandable semantics:

- Archive hides a conversation from the main list and is reversible.
- Delete moves chat history and its task copies to Trash, with Undo and Restore. Stop an active run before moving it. Explain when uncommitted task work is included.
- Removing a project from the sidebar removes the reference; it never deletes the source repository or its commits.
- Permanent deletion is a separate, explicit action. No silent cleanup of saved work.

**Acceptance:** rename, archive, delete, undo, restore, and find an older chat without using a terminal. The current task title is the most prominent navigation label.

## 3. Permissions: ask once for a meaningful scope

**This feature partly exists already.** “Allow for this session” currently remembers an exact argument list in one task workspace. It survives pause/resume and follow-ups, but not a server restart, another chat, or replacement of the task workspace. A different test selector or flag asks again. “Run once” is currently the visually primary action.

That behavior is implemented and covered by [permission tests](tests/test_permissions.py). We should first reproduce any case where the *identical* command, workspace, and live server session still asks twice. That would be a bug, not a reason to add a second permission system.

### Proposed user-facing choices

| Choice | Meaning |
| --- | --- |
| **Allow project tests for this session** | Permit the displayed test-runner profiles for this selected project until CheapOS exits or the grant is revoked |
| Run once | Permit this command only |
| Decline | Do not run it; keep the work saved |

Make the session option prominent for recognized project test runners. Put a small **Tests allowed this session** control beside the composer, with the scope and a revoke action. Show automatic runs in the chat: “Running tests · allowed for this session.” Permission should remove clicks, not visibility.

Implement this as structured runner profiles, rather than a broad shell prefix:

- Identify the project, executable, runner, permitted test roots, supported selectors/flags, and relevant configuration.
- Start with standard-library `unittest`; add pytest and named package scripts deliberately.
- Permit ordinary changes of test selector or verbosity within the approved profile. Canonicalize equivalent commands without accidentally widening access.
- Do not make `python *`, `python -c`, arbitrary shell commands, package installation, or Git writes part of a test grant. Tests still execute repository code, including agent-edited code; the one-time scope explanation must say so plainly.
- A project-session grant can cover CheapOS-created copies of that same project. Check the approved runner/configuration when a copy is replaced or reconciled; an unrelated workspace or changed script definition must not silently inherit permission.
- Expire at server exit; support revocation. Persistent project trust can be a later, separate opt-in.

Keep **command authorization** separate from **test-result reuse**. Permission lets an authorized check run again. Reuse means it does not need to run again because the relevant code and environment are unchanged.

**Acceptance:** authorize project tests once; run a focused test, another test in the approved roots, checkpoint verification, and a follow-up without another permission dialog. An unrelated command still asks. A restart clears the grant. Every execution remains visible.

## 4. Limits should guide the controller before interrupting the operator

We have accumulated many overlapping limits: money, review tokens, output tokens, worker turns, checkpoint turns, review rounds, run time, repeated reads, and handoffs. Their individual purposes are reasonable; their combined user experience feels like a machine repeatedly asking to be restarted.

One concrete mismatch: the default checkpoint interval is **12 turns**, independently of the overall worker-turn allowance. Raising the latter to 100 does not remove the former. The UI should never make people discover this through failure.

### Proposed behavior

| Situation | CheapOS should do |
| --- | --- |
| Repeated unchanged inspection | Show the saved evidence to the worker and request the next concrete action; compact context or try a qualified alternative within the agreed recovery budget |
| Checkpoint interval reached | Take stock automatically: answer a question, verify an eligible change, or form a small continuation step. Treat this as an internal scheduling boundary before escalating it to the user |
| Output truncated or malformed tool arguments | Preserve files, discard incomplete calls, retry a smaller action with supported model settings; do not ask the operator to repair JSON or copy hashes |
| Tests failed | Feed the failure and relevant lines back to the worker for a bounded repair attempt |
| Reviewer requests changes | Continue the revision loop within the existing task envelope |
| No working free route | Show one clear explanation, the next eligible retry time, and a cancelable retry option. Do not make the user click Resume repeatedly during a known cooldown |
| No meaningful progress after bounded recovery | Ask one specific question, show the attempted approaches and saved work, and explain what decision would unblock it |
| Explicit spending/time ceiling or user Pause | Stop and preserve state; never silently raise the ceiling or move from free/local to paid/remote |

Keep a visible **Free only** or spending choice and a simple working-time choice. Move technical counters to advanced settings. Internal repairs and model switches count toward the same envelope; “automatic” must not mean infinite retries. The existing anti-loop checks should become inputs to recovery, not simply disappear.

Start with two understandable presets: **Interactive** for short feedback cycles and **Extended** for longer work under an explicit time limit. Validate extended runs before promising unattended overnight delivery.

**Acceptance:** a supported small change reaches review without manual Resume clicks caused only by internal checkpoint counters. A genuine budget stop, unavailable route, or lack of progress has a specific explanation and useful next action.

## 5. Make verification fast enough to support the workflow

There are two separate problems: CheapOS's own development suite is slow, and agents can choose overly broad or repeated verification commands in projects.

### The app's development suite

The last Python run took about **4 minutes 56 seconds**. JavaScript checks were much faster. Code inspection shows repeated temporary Git repositories/snapshots, real process execution, HTTP fixture teardown, durable state writes, and a deliberate 120 ms pause in the scripted demo provider. These are profiling candidates; we have not measured their individual share of the runtime.

There is also a real configuration mismatch: `Workspace.run_checks` defaults to **90 seconds**, shorter than that full Python suite. Selecting the whole suite inside CheapOS can therefore time out even when individual tests are healthy. Fix runner-specific timeouts and test selection together; lowering safety margins or repeatedly retrying the same timeout will not help.

Proposed work:

1. Add per-test and setup/teardown timings; publish the slowest cases and suite totals locally.
2. Separate fast logic tests, integration tests, and full end-to-end scenarios. Keep some real Git/process/network-boundary tests; avoid paying for them in every logic test.
3. Make the demo's pacing configurable so production demo visuals can remain readable while automated fixtures run without cosmetic delays.
4. Replace avoidable polling with events where appropriate. Measure fixture setup, persistence, and HTTP shutdown before optimizing them. Keep durability and restart tests using real persistence.
5. Provide a documented fast developer command and focused test selection. Update CONTRIBUTING to distinguish documentation, frontend, controller, and commit/recovery changes.
6. Run the relevant set after an edit. Run the complete suite once at the appropriate integration/release boundary, not again for every unchanged stage.
7. Consider parallel test processes only after fixtures and shared resources are isolated. More concurrency is not automatically faster on the laptop running a local model.

**Initial targets, not current promises:** fast checks under 10 seconds; most focused changes verified in under 30 seconds; reduce the full suite toward two minutes. The runner must allow the measured full-suite duration when that suite is actually required.

### Tests inside an agent task

Choose verification from project guidance and the changed behavior. During a repair, run the focused failing test first, then the relevant regression set. Documentation-only work can use appropriate documentation checks rather than inventing a code test requirement.

Passing evidence should record the task baseline/content identity, command, working directory, environment/dependency identity, outcome, and time. Invalidate it when relevant inputs change. CheapOS already reuses a passing check at a checkpoint for the same patch/command and task generation, and commit approval already avoids rerunning tests. Extend that system rather than creating a second test scheduler.

By the final human decision, verification and model review should be complete. Human approval should apply and commit the reviewed result. If reconciliation changes the code, verify and review the reconciled result before returning it for approval. A short Git consistency check is different from rerunning the test suite.

**Acceptance:** no full-suite rerun just because the task moved from worker to reviewer to human approval. Failed or stale evidence never displays as passing. One clearly diagnosed timeout does not become a repetitive retry loop.

## 6. Empower the agents with better context and tools

The biggest improvement is likely fewer wasted turns, not more turns.

- **Start with a compact project brief:** languages, entry points, test commands, dependency status, current request, and relevant files. Cache it against project changes. Avoid repeated broad exploration in an established chat.
- **Keep a small working plan:** next step, completed evidence, remaining requirements, current file versions, and open failures. This should survive a handoff without replaying the whole conversation.
- **Make small edits the easy default:** use the compact edit machinery proactively when model capability or file size warrants it. The controller owns file-version tracking and syntactic validation; the model supplies intent and replacement content.
- **Offer the tools needed for the current step:** exploration, implementation, verification, and review have different needs. Keep a path to request missing evidence rather than forcing guesses.
- **Select for completion:** use observed successful tool calls, edits, checks, review outcomes, latency, and failure rate. The first free catalog entry or a model name containing “mini” is not a quality score. Track effective cost per accepted task, including retries.
- **Use reasoning selectively:** brief local conversation and simple edits can use lighter supported settings; difficult repairs and review may need more. Lowering output limits blindly can increase truncated calls and total work.
- **Give the reviewer precise evidence:** requested behavior, current diff, relevant code, test results, and uncertainties. Preserve a genuinely separate reviewer request and visible model identity; provide a way to inspect missing context.
- **Turn environment problems into setup actions:** detect missing dependencies or test runners early and offer a scoped setup flow. Current dependency preparation is manual; workers should not spend turns rediscovering that.
- **Keep local chat lightweight on laptops:** Gemma can greet and delegate, then idle. Hardware-capable users can deliberately choose all-local work. Report measured responsiveness rather than claiming localhost is automatically fast.

Keep the controller deterministic where possible: pause, permission decisions, test-result validation, commit consistency, and recovery accounting should not require extra model conversations.

## 7. Onboarding: one short path to useful work

Recommended experience:

1. **Open CheapOS.** Detect Python/Git requirements through the launcher and show an actionable remedy if needed. Remember existing projects and connections.
2. **Choose where AI runs:** “Use OmniRoute — recommended for free remote models” or “Use models on this computer.” Keep advanced direct endpoints behind an option.
3. **Connect with guided progress.** For OmniRoute, detect an existing compatible instance, reuse it, or start the installed CLI. If missing, offer a clear guided installation flow that checks Node and explains what it installs. Do not ask the user to assemble endpoints and two model IDs.
4. **Finish provider setup only if needed.** Open OmniRoute at the relevant setup page if supported, explain dashboard login versus client API key, then return to CheapOS automatically when connectivity is ready. Preserve all completed setup steps after an error.
5. **Open a project and chat.** Select a responding free worker automatically and check a distinct reviewer when coding needs one. Ask for the useful project-session test scope when tests first become necessary.

A successful greeting should say the connection works. It must not imply the edit/check/review workflow was validated. Offer **Try a sample task** to exercise that loop in a disposable repository with visible progress and no project risk. Show whether it is a scripted demo or a real model run.

For local-only use, detect installed models and show which can actually use tools. If none are installed, offer model guidance and explicit download choices with size/hardware context. Keep a scripted demo available without installing a large model. Never silently send a local-only project to a cloud provider.

Default to free-only for this alpha. Free route availability changes; onboarding should discover and verify it rather than ship a stale list. Keep a known working connection sticky so each launch does not become another selection exercise.

The installed OmniRoute inspected for this check-in is **3.8.49**. Upstream documentation linked below includes a newer `release/v3.8.51` branch. Capability detection and versioned integration tests matter; documentation for a newer version is not evidence that the installed gateway exposes the same APIs or has those features enabled.

**Acceptance:** with OmniRoute and one working provider already configured, a new user opens a project and reaches a useful first response without entering endpoint URLs or choosing worker/reviewer model IDs. Test fresh install, existing gateway, missing provider, wrong client key, port conflict, local-only, and offline recovery.

## 8. What to take from the video

I reviewed the [video's auto-generated transcript](https://www.youtube.com/watch?v=MfH0jNStIzU) and the projects' current documentation. The video proposes input compression, terminal-output filtering, shorter replies, smaller implementations, lighter models, and orchestration. It distinguishes command/output savings from total-token savings and recommends testing them. Its approximately 80% combined result is the presenter's claim, not a CheapOS measurement.

| Idea | Fit for CheapOS | Recommendation |
| --- | --- | --- |
| **RTK** | Filters command output before it returns to an agent | First optimization experiment: concise test results for the model, with failing cases/tracebacks preserved and raw output still available to the operator. [Upstream RTK](https://github.com/rtk-ai/rtk) |
| **Headroom** | Compresses tool/context inputs; offers library, proxy, and retrieval of originals | Evaluate after measuring our own context growth. Prototype one optional integration point and verify retrieval, edit accuracy, and cache behavior. Do not make another proxy mandatory for onboarding. [Headroom](https://github.com/headroomlabs-ai/headroom) |
| **Caveman** | Terse output instructions; the current project also includes proxy/compression features | Borrow concise worker reporting first. Keep CheapOS conversational and clear. Never compress tool JSON, exact edit text, or failure evidence indiscriminately. Its CLI currently documents default anonymous telemetry, which would need explicit handling before bundling with a no-telemetry app. [Caveman](https://github.com/JuliusBrussee/caveman) |
| **Ponytail** | Encourages the smallest sufficient implementation and reuse of existing code | Adopt the principle in worker instructions: satisfy all requirements with a focused diff, avoid speculative abstractions, preserve useful tests. Evaluate the skill as an optional addition, not a compulsory runtime service. [Ponytail](https://github.com/DietrichGebert/ponytail) |
| **Lighter models and orchestration** | Already the central CheapOS architecture | Improve selection using task outcomes and stage needs. A stronger paid route remains an explicit later choice; keep current experiments free-only. |

### Avoid duplicating OmniRoute's pipeline

Current upstream OmniRoute documents RTK-style filtering, Caveman-style compression, a Headroom-named engine, and output styles including Ponytail. That overlap is worth evaluating before adding standalone dependencies. These integrations are not automatically identical to the standalone projects. See its [compression engines](https://github.com/diegosouzapw/OmniRoute/blob/release/v3.8.51/docs/compression/COMPRESSION_ENGINES.md) and [compression guide](https://github.com/diegosouzapw/OmniRoute/blob/release/v3.8.51/docs/compression/COMPRESSION_GUIDE.md).

Its [RTK documentation](https://github.com/diegosouzapw/OmniRoute/blob/release/v3.8.51/docs/compression/RTK_COMPRESSION.md) describes filtering output already captured by the client, and explicitly distinguishes that from full compatibility with the RTK executable and shell hooks. That fits our architecture: CheapOS should retain control of command approval, exit status, and verification evidence.

Proposed division: CheapOS selects relevant context and records authoritative results; the chosen gateway may perform an explicitly configured compression pass. Preserve original output for retrieval and review. Identify which layer compressed which content so we do not double-compress or count the same savings twice. Direct-local users should still benefit from CheapOS's own concise tool results without OmniRoute.

**Evaluation rule:** change one thing at a time. Keep the task, model pair/settings, source baseline, and acceptance tests comparable; record gateway settings and repeat trials because model output varies. Compare raw baseline, concise reporting, output filtering, then optional context compression and their combination. Compression earns a default only if task success and evidence quality remain acceptable.

Reducing 90% of one log does not reduce 90% of the run. Input/output/cached/reasoning tokens, context overhead, retries, latency, and final correctness all matter. Compression also does not make the underlying test process execute faster. Replace the UI's fixed hypothetical “Saved ~$…” calculation with actual usage and, when available, a clearly defined measured comparison.

## 9. Ordered implementation plan

Each milestone should be a small set of reviewable changes with a before/after demonstration. This document does not authorize installing the video tools or changing runtime permissions now.

| Order | Deliverable | Completion evidence |
| --- | --- | --- |
| **1 — Daily usability** | Task-title header; rename/pin/archive/delete/restore; readable complete sidebar history; prominent existing session approval | Browser flow covers navigation, older chats, unsaved work, active-task handling, deletion and undo; source repo untouched |
| **2 — Permission and verification pass** | Reproduce repeated approvals; structured project-session test profiles; test timings and fast/focused/full commands; suitable command timeouts | One grant covers expected test variants; unrelated commands ask; targeted checks are faster; current full suite can finish when selected |
| **3 — Controller recovery** | Separate soft progress thresholds from hard limits; short recovery explanations; bounded no-progress handling and cooldown retry | A stalled worker recovers without repeated operator Resume clicks, or stops once with an actionable reason; budget and saved work remain correct |
| **4 — Guided first run** | OmniRoute detection/start/setup-return flow; automatic role selection; local-only alternative; sample task | A fresh user completes setup and understands what is running, where code is sent, and whether the full loop passed |
| **5 — Agent efficiency** | Project brief, compact handoff state, stage-appropriate tools, proactive small edits, outcome-based model ranking | Repeatable tasks use fewer wasteful reads/turns and complete with fewer interventions |
| **6 — Measured optimization** | Baseline benchmark set; optional RTK/output filtering; then Headroom/other compression only if justified | Report end-to-end success, human interruptions, elapsed time and total usage; no extrapolated percentage claims |

Prioritize milestones 1 and 2 next. They address the things already making everyday use frustrating and make the remaining controller work cheaper to build and verify.

## 10. Scorecard for the next check-in

Use a fixed starting set: a README edit, a small utility with tests, a bug fix, a public-link question, a failed-check repair, a reviewer revision, and a commit conflict. Include scripted fault cases plus separate real-model trials. Do not use this same set as the only long-term benchmark.

Record per task:

- Completion against the original requirements, not simply “model stopped” or “reviewer said approve.”
- Unnecessary approval/resume clicks; target **zero repeated test approvals after a valid grant**.
- Time to first useful visible activity, total completion time, and time waiting for the operator.
- Worker/reviewer turns, repeated reads, failed tool calls, handoffs, and recovery attempts.
- Check count and duration; whether evidence was rerun or correctly reused.
- Total input/output/reasoning/cached usage where reported, provider-reported versus estimated cost, and local resource impact.
- Onboarding steps, setup failures, and whether a new user knows what to do next.

**Definition of the next good version:** a person can connect, open a project, request a small change, watch understandable progress, authorize tests once, and approve a ready commit—then naturally continue. When something fails, CheapOS owns recovery until it needs a real human decision.
